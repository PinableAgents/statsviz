# 本轮容量与性能复核

## 查询基线

已有稀疏聚合夹具（并非全量原始数据），20次Range：p50 682.663ms、p95 695.937ms、最大710.294ms；每次Go累计分配259615024字节。数据随保留窗口前进，本轮返回161点、1h、779209字节。没有清理OS cache。

CPU profile显示50% rawsyscall、30.6% madvise。modernc读取35～47KB聚合payload会超出16384字节的小块分配阈值，产生频繁mmap。仅按run主键读取仍p95 589.913ms，不能单靠索引达成目标。

## 写入基线

真实runtime默认快照形状、523数值单元、1951字节payload，保持同一快照以衡量存储路径：

- 3600条，60条一批Enqueue/Flush：2.298秒，1566条/秒，累计Go分配5.42GB，DB约33.1MB，无丢样或写入错误。这是加速批量写入能力，不能当作每秒单条写入开销。
- 600条，每条Flush：3.110秒，累计Go分配2.43GB，DB约5.7MB，无丢样或错误。这是加速单条提交测试，没有模拟一秒墙钟等待，也未测系统常驻CPU。

## 已修复：启动扫描

`recoverTails` 当前JOIN与相关max(seq)查询的EXPLAIN为 `SCAN s USING INDEX samples_run_time`，对每一行samples求相关子查询并查runs。虽然最后只返回每个未封存运行的尾样本，实际读取工作仍随完整样本数增长，与设计的恢复工作量描述不符。应先从未封存runs逐run按PRIMARY KEY ORDER seq DESC LIMIT 1读取尾部，并补充EXPLAIN回归；正常结束的run不应触发全样本扫描。

## 已修复：Point 向后候选扫描

`ts_ms >= cutoff AND ts_ms >= at` 的两个下界中，SQLite只将第一个用于索引定位，再逐条过滤第二个。3600条smoke中间时间的向后候选实际执行约10800 VM步骤、12.21ms；向前候选不足100步、0.055ms。两者的EXPLAIN QUERY PLAN均显示SEARCH，因此仅断言命中时间索引无法捕获此问题。应将向后下界先在Go中合为max(cutoff,at)，并将指定run的SQL拆成明确run_id条件与运行内时间索引，避免扫描不相关运行。

## 验收工具复核要点

- 冻结时钟必须覆盖Open中的首次cleanup，复用完整fixture不能因真实时间前进先删除数据后才设置now。
- 原始样本必须经实际Enqueue/Flush与聚合路径写入，不能用直接SQL批量构造聚合代替全量写入验收。
- 已完成与未完成fixture分别标记；拒绝覆盖不属于工具的数据库。
- p95、分配与大小必须报告测量边界，区分加速批量吞吐、单条提交开销、首次调用和预热重复。

## 已完成的修复与评审结论

- 恢复改为先读取未封存运行，再逐运行按主键取最高 seq 尾样本；先关闭 run rows、收集 tail，之后启动重建事务，避免单写连接自锁。正常关闭、空运行和墙钟回拨均有回归覆盖。
- Point 全局与限定运行拆为四条明确 SQL；后候选只以 max(cutoff,at) 作为时间下界。原 10826 个 VM 步骤降到 21 个（全局）/23 个（指定运行）；回归验证实际 SeekGE 键寄存器，覆盖仅检查 SEARCH 会漏掉的退化。
- 聚合私有格式改为带版本、数字 kind 的九项 tuple。旧 object 与新数组混合可读；原始 JSON 和对外协议保持一致。整数时长/计数精确解析，非法标量和未知版本拒绝。
- 在 963 个聚合桶的复制库中逐桶 roundtrip 和完整 Range 响应 DeepEqual；payload 45376710→13988922 bytes（减少69.2%）。抽样20轮 p95 695.937→415.773ms，分配259615024→206606197 bytes。该夹具不是604800原始样本，且查询边界随墙钟有变化，不作为全量证明。
- 专项只读评审发现 fixture ID 未绑定 wire 版本。已将 aggregatePayloadVersion 纳入 ID、工具格式与固定文件名改为 v2，回归确认 wire 版本变化必然改变 ID。旧 v1 数据不会参与新格式全量测试。
- 固定时钟在 Open 首次 cleanup/recover 之前设置；实际公共 Open 继续使用 time.Now。

全部修复已通过定向验证；全量实测与最终检查见任务实现说明和容量验收文档。

## 全量验收暴露的关闭写放大

首轮通过真实写入生成 604800 条 raw、60480/10080/1008 行三层 rollup，功能与 180 次幂等重写/5 次 Range 并发通过，随后 Close 超过 10 秒。原因是 `sealOpenRuns` 对未结束运行的全部 71568 个聚合桶无条件 UPDATE，即使所有桶已为 `is_final=1`，仍重写约 1.2GB 聚合 payload。修复给更新加 `is_final=0`，不改 schema；完整库只读过滤约 0.2 秒。回归用触发器捕获 UPDATE 事件，约束已封存桶与已结束运行不被更新，同时验证未封存桶与结束时间语义。

首轮构建报告保留在 `/tmp/statsviz-history-full-1016-before-seal-fix.json`。后续复用全部生成的数据必须再次执行所有功能、并发和 Close/reopen 断言，不得通过人工标 complete 跳过失败步骤。

## 最终评审与输入数值修复

最终只读复核确认封存过滤、单运行聚合主键读取及安全复用无高置信度回归，同时发现合法JSON巨大指数（1e999999）超出聚合ParseFloat范围，会让失败pending持续重试。已在入队快速类型校验后增加有限float64检查，拒绝该样本；仅验证数值、不改写原始JSON。API回归验证拒绝后合法的9007199254740993仍可Flush并按原字节持久化，避免阻塞后续样本。更新后的523维校验基准中位数为85803ns/op、57171B/op、780allocs/op，较初始分配减少95.7%。

604800最终全量报告 passed=true，默认global7d p95为467.062ms、globalPoint为0.366ms；完整新建3600条fixture另行验证最终写入路径。数值范围修复仅影响Enqueue输入检查，完整库查询结果与已记录性能不受影响。
