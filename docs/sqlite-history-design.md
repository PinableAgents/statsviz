# 基于 SQLite 的 7 天监控历史设计

状态：已编码接入。实际接入示例见 [history/main.go](../_example/history/main.go)，字段契约见 [history-implementation-contract.md](history-implementation-contract.md)，表结构见 [sqlite-history-schema.sql](sqlite-history-schema.sql)。下文同步实现取舍；交付验证见第 12 节。

## 1. 目标与边界

- 保留最近 7 × 24 小时的原始采样数据，超过窗口滚动清理。
- 支持实时监控、历史区间、历史时间点快照以及放大后查询细节。
- 浏览器关闭期间继续采集，刷新页面和正常重启后可查询已落盘数据。
- 默认每秒采集一次，沿用 `SendFrequency`；更高采样频率需要重新计算容量。
- 7 天内的原始样本不因生成聚合数据而降精度。长窗口只降低显示精度。
- SQLite 随进程使用，历史功能显式启用，数据库路径由接入方指定。
- 第一版覆盖单个应用实例的连续运行历史；一个数据库文件同时只允许一个采集实例写入。
- 当前已有 `Index()`、`Ws()` 和框架自定义注册方式，新增接口必须兼容这些方式。

本方案不包含系统级 CPU、任意函数耗时或完整事件追踪；可查询指标仍来自当前 Go runtime 和用户自定义图表。当前 `lastgc` 仅是采样时看到的最近一次 GC 时间，不能据此还原全部 GC 事件。

## 2. 改造前基线与接入位置

- `statsviz.go`：定时调用 `plots.WriteTo()`，将 JSON 通过 WebSocket 广播，尚未落盘。
- `internal/plot/list.go`：采集、计算速率/增量和 JSON 编码集中在 `WriteTo()`。
- `internal/static/src/app.js`：建立 `StatsManager(600, cfg)`，默认仅缓存 10 分钟。
- `StatsManager.slice()`：按点数截取，无法表达任意起止时间。
- `PlotManager.update()`：以最新样本为时间轴终点；`plotConfig.js` 禁止横向缩放和平移。

将采集拆成一次 `Collect()`，得到不可变快照，然后分别供实时推送和历史存储使用。兼容保留 `WriteTo()`，但采集循环不得为两个消费者分别调用它：速率、增量函数均有状态，重复读取会改变结果。

入队校验完整 JSON 语法、对象/数组结构及 number/null 类型，不为每个数值新建 Decoder，有限数值检查不改写原始JSON；523维快照的校验分配已由约1.33MB降至57KB/次。

```text
定时采集 → 不可变快照（run_id、seq、UTC 时间、实际间隔、series）
             ├─ 编码一次 WebSocket 消息 → 实时浏览器
             └─ 有界队列 → 单写入协程 → SQLite 原始快照与聚合

历史 HTTP 查询 → SQLite 时间索引 → 选择粒度/裁剪指标 → 浏览器
```

运行时直方图数组可能复用，入队前必须复制，或者先编码为不可变字节。队列不得持有下一次采集会修改的内存。`seq` 在采集时分配，不能在落盘时才分配，否则无法识别落盘丢样。

## 3. Go 组件与配置

采用 `database/sql` 和 `modernc.org/sqlite`，避免为跨平台构建新增 CGO 要求。实施时锁定兼容当前 Go 1.25 的驱动版本。

SQLite 适配器放在独立的 `history/sqlite` 包，公共采样模型和小型存储接口放在 `history` 包。主包依赖接口，适配器不被主包直接导入；仅使用原有实时监控的程序不会链接 SQLite 驱动。

实际用法如下：

```go
store, err := sqlitehistory.Open("/app/data/statsviz.db", sqlitehistory.Options{
    Retention:     7 * 24 * time.Hour,
    FlushInterval: time.Second,
    QueueCapacity: 60,
})
if err != nil {
    return err
}
defer store.Close()

srv, err := statsviz.NewServer(statsviz.History(store))
if err != nil {
    return err
}
defer srv.Close() // 先停止生产、等待采集退出并刷新队列，再关闭 store。
srv.Register(mux)
```

数据库由调用方持有和关闭；`Server.Close()` 停止采集并等待历史刷新，不擅自关闭外部传入的存储。数据库创建、目录权限或迁移失败应在初始化时返回错误。

存储接口至少表达 `StartRun`、非阻塞入队、`Flush`、元信息查询、区间查询和单点查询。只有 Flush 成功或返回的已提交水位才能表示已落盘；入队成功不能表示持久化成功。清理、聚合和连接管理由 SQLite 适配器负责，不进入采集循环。

首版默认参数建议：

| 参数 | 默认值 |
| --- | --- |
| 保留窗口 | 7 天 |
| 写入刷新条件 | 1 秒或 60 条，任一满足即提交 |
| 待写队列 | 60 个采样快照 |
| 连接数 | 1 个写连接，最多 2 个读连接 |
| 定期清理 | 每 1 分钟触发，每批最多 5000 个原始快照 |
| 查询超时 | 2 秒 |
| 单曲线点数 / 热力图时间列 | 最多 1500 / 400 |
| 单次响应总数值单元 | 最多 300,000，包含峰值包络等附加序列 |
| 单次响应体积 | 压缩传输前的 JSON 最多 8 MiB |
| 查询元数据 | 最多 4096 个运行、10000 个缺口，合计最多 8 MiB |
| 单次运行配置 | 图表配置与聚合声明合计最多 1 MiB |

这些限额由服务端约束。数值数据超预算时优先调整粒度；仍无法满足时返回错误，不能靠浏览器接收完整数据后再裁剪。元数据在读取时限制行数与累计字节，超限返回明确错误；区间查询只预检一次固定元数据，随后加粗重试仅编码数值点。默认编码先使用 JSON，zstd 由实测结果决定是否默认开启。

## 4. 数据模型

采用“每次采集一行快照 + 每个时间桶一行聚合”，避免将热力图每个桶拆成独立 SQL 行。默认每秒一次，7 天原始快照共 604,800 行，与一份快照包含多少指标无关。

| 表 | 内容 | 查询方式 |
| --- | --- | --- |
| `runs` | 每次运行的起止时间、采样间隔、图表配置、聚合语义及格式版本 | 主键 |
| `samples` | 每个采样点的完整原始快照 | `(run_id, seq)` 主键，全局时间和运行内时间索引 |
| `rollups` | 10 秒、1 分钟、10 分钟三个层级的全部图表聚合 | 运行、粒度、桶起点主键及时间索引 |
| `gaps` | 队列溢出、存储故障等造成的已知缺口 | 时间索引 |

时间戳统一为 UTC Unix 毫秒，真实采样间隔以单调时钟的纳秒差计算。时间戳允许重复，样本身份由 `(run_id, seq)` 唯一确定。明显的系统时间跳变应分段展示，不能由墙上时钟差计算速率。

每次启动建立新的 `run_id`，增量和累计直方图不跨运行求差。`config_json` 保存当时的图表、单位和桶边界；`aggregation_json` 声明各子序列的聚合类型。配置哈希覆盖两者，历史数据不会被新版配置误读。

原始 payload 保存实际采样值，累计直方图的相邻差分在存储聚合时计算，不修改既有 WebSocket 的 `series`。首个无法求差的直方图单元返回 null，不能伪装成观测到零次事件。

当前版本使用 JSON 编码，schema 为后续压缩预留 `zstd-json`，本次不启用压缩。原始整数编码不通过浮点转换，避免持久化阶段引入额外精度损失；聚合统计使用 float64。

聚合 payload 使用内部带版本的紧凑格式 `[1,{plot:[[kind,hasValue,weightedSum,weightNS,sum,min,max,last,count],...]}]`，kind 编号 0～4 依次对应 gauge、rate、delta、histogram、event。固定位置省去每个数值单元的重复字段名，时长和计数按 int64 读取。表结构与 `codec=json` 不变，原始快照、HTTP 和 WebSocket 格式不变。新程序同时读取旧 `{"plots":...}` 聚合对象和 v1 数组，旧库无需重建；旧程序无法读取新写入的数组聚合，因此降级前必须保留升级前的数据库副本。

## 5. SQLite 连接、写入与恢复

建议参数：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 2000;
PRAGMA foreign_keys = ON;
```

采用一个写连接和最多两个只读查询连接。`foreign_keys`、`busy_timeout` 等连接级参数必须初始化到每个连接，不能只对连接池执行一次 `Exec()`。读取连接设置 `query_only=ON`。

- 正常每 1 秒或累计 60 条时提交一批；达到任一条件即提交。
- 同一事务写入样本、已知缺口及受影响的聚合桶。重试以 `(run_id, seq)` 幂等，聚合桶写入完整替换结果，不重复累加。
- 原始样本更新受影响的 10 秒桶，再逐级合并为 1 分钟和 10 分钟桶；合并保留加权和、覆盖时长和极值，不用“平均值再平均”。
- 当前未闭合桶也随事务更新；`is_final` 只代表桶不再变化，完整程度由覆盖信息和缺口判断。
- WAL 支持恢复已提交事务；进程异常退出时，尚未提交的队列数据可能丢失。当前固定使用 `NORMAL`；它的断电持久性弱于 `FULL`，本次未暴露同步级别选项。
- 重启不继续使用上次运行的速率基线。先读取未封存的运行，再为每个运行按主键 `ORDER BY seq DESC LIMIT 1` 取尾样本，只重算尾部 10 秒桶及其父桶并封存。正常结束的运行不参与恢复，避免从全部 samples 行筛选每个运行的末尾。
- 正常关闭和下一次启动均会封存未结束运行。结束时间取该运行最高已持久化序号的样本时间，空运行取自身启动时间，避免把停机时长算作数据覆盖；墙钟回拨时允许结束时间早于启动时间，查询按实际样本覆盖选取运行。
- 封存只更新这些运行中 `is_final=0` 的聚合桶。已封存的桶不再重写，避免正常关闭时为全部七天聚合 payload 再写一遍 WAL。

队列满时丢弃最旧的待写样本，保留最新监控数据，并记录丢失的序号区间。写入失败不能终止实时采集；失败期间暴露状态，恢复后补记缺口。无法恢复的磁盘损坏不能只靠重试掩盖，应停止历史写入并返回明确错误状态。

`Server.Close()` 停止生产并等待采集协程退出，再有超时地刷新队列。关闭或刷新失败返回错误，不能把尚未提交的数据报告为已落盘。

## 6. 聚合语义与显示精度

聚合类型显式定义到子序列，不根据图表的 bar/scatter/heatmap 类型猜测。同一个 Goroutine 图中可能同时存在即时总量和创建次数增量。

| 指标类型 | 桶内处理 | 展示 |
| --- | --- | --- |
| 内存、Goroutine 数等 gauge | 保存时长加权和、覆盖时长、min/max/last | 平均趋势和峰值范围 |
| CPU、分配速率等 rate | 按实际有效间隔加权，保存 min/max | 原有每秒单位，补充峰值 |
| CGO、GC 次数等 interval delta | 求和，保存有效覆盖时长 | 区间总量；换算速率时明确单位 |
| 累计延迟 histogram | 同一运行内先求相邻采样差，再按桶合并 | 区间分布热力图 |
| 活对象 size-class 分布 | 作为每桶 gauge 聚合 | 平均或末值分布，不累计求和 |

自定义序列默认按 gauge 处理，提供声明其他聚合语义的入口。缺失数据不记为零；缺口两侧不连线，累计直方图也不把跨缺口的差值任意分配到某个时间桶。桶级统计保留覆盖信息，界面能区分低负载与没有观测。

默认显示建议：

| 范围 | 主要数据源 | 默认粒度 |
| --- | --- | --- |
| 1m / 5m / 10m | 原始样本 | 实际采样间隔，按点数上限调整 |
| 1h | 聚合 | 10 秒 |
| 6h / 24h | 聚合 | 1 分钟 |
| 7d | 聚合 | 以 10 分钟桶合并；按所选维度、热力图和总数值预算调整，完整指标集通常更粗 |
| 放大历史局部 | 更细一级聚合或原始样本 | 按新视窗重新选择 |
| 历史时间点 | 原始样本 | 最近的有效实际样本 |

普通曲线每条上限约 1500 个点，热力图时间列上限约 300～500。多维 min/max 若来自不同时刻，不能拼成堆叠总量；堆叠图使用同一桶的平均分量，各分量极值在 tooltip 和误差范围中单独展示；本版不保存峰值发生时间。选中聚合桶时展示区间摘要，钻取具体时间后才展示原始单点值。

需要 30 分钟、1 小时等更粗显示粒度时，合并已保存的 10 分钟桶；合并使用加权和、覆盖时长、极值及计数等可合并状态，不直接平均各桶均值。新桶边界与基础桶对齐。最终点数预算包含峰值包络或额外曲线带来的数据量，不能只统计主曲线。

查询区间统一为 `[from, to)`。只有完全落入查询范围和保留窗口的整桶可直接复用聚合结果；首尾未对齐桶逐级使用更细聚合，最终小于 10 秒的边界由原始数据重算，不能把范围外数据混入统计。三个聚合层级的窗口对齐到 UTC，避免时区和夏令时改变桶宽。

## 7. 7 天滚动清理与磁盘管理

每分钟计算 `cutoff = now.UTC() - retention`，每轮删除最多 5000 个过期样本，让周期之间的实时写入正常推进：

```sql
DELETE FROM samples
WHERE (run_id, seq) IN (
    SELECT run_id, seq FROM samples
    WHERE ts_ms < ?
    ORDER BY ts_ms, run_id, seq
    LIMIT 5000
);
```

聚合桶仅在整个桶早于 cutoff 后删除；跨边界的桶可以留待下次清理，但查询不能直接使用其过期部分。缺口记录按结束时间清理，跨窗口缺口在响应中裁剪。没有样本、聚合或缺口引用的运行配置才可删除。

查询层立即限制到最近 7 天，物理清理可以稍后完成。服务重启后先清理一批过期数据，再进入常规循环；大量过期积压会分多轮回收。不能为满足磁盘预算悄悄删除 7 天内的数据。

SQLite 删除行后释放的页通常留在文件中供后续写入复用，文件达到稳定负载的高水位后复用空间；这不等于磁盘文件会每日缩小。常规运行不执行全量 `VACUUM`，避免长时间阻塞和额外磁盘需求。需要主动缩小时，可在首次建库前开启 incremental auto-vacuum，并在低负载时小批回收。

使用短读事务和有时限查询，避免长期读事务阻碍 WAL checkpoint。定期执行被动 checkpoint，空闲时才考虑截断；`journal_size_limit` 不能作为活跃 WAL 的硬上限。

磁盘容量按实际 JSON 样本估算。若单条为 1～4 KiB，默认频率下原始 payload 约 0.58～2.31 GiB，另加页、索引、聚合及 WAL。该范围是计算示例，不是容量承诺；250ms 采样会使原始记录数约增加到四倍。

状态接口报告实际文件和 WAL 占用。当前不提供磁盘软预算选项；写入失败时保留实时监控，暴露错误、队列及丢样状态，并重试待提交事务。有限磁盘与任意指标数量下，不能承诺无条件保留全部 7 天数据。

## 8. 历史查询接口

所有路径跟随 `Root()`，默认位于 `/debug/statsviz/` 下。提供独立 handler，供自定义 HTTP 框架注册，并沿用现有监控路由的访问控制。

| 接口 | 用途 |
| --- | --- |
| `GET history/meta` | 可用起止时间、运行列表与配置、实际采样间隔、存储状态和已提交水位 |
| `GET history/range?from=...&to=...&plots=...&max_points=...` | 返回所选指标的区间原始值或聚合值 |
| `GET history/point?at=...&run_id=...&tolerance_ms=...` | 返回指定时间附近的一份原始快照 |

时间参数为 UTC Unix 毫秒。range 响应包含请求范围、实际范围、粒度、聚合类型、覆盖信息、缺口以及 `(run_id, seq)` 水位。max_points 是每条曲线的预算，不是调用方绕过服务器限制的开关；还需限制图表数、总返回单元数和最大响应体积，预算不足时返回更粗粒度或明确错误。

同一次响应的数据、配置和水位在同一个短只读事务中读取，避免并发写入或清理造成不一致。每个运行分别报告水位，不能将多个运行的 seq 当成全局连续序号；水位之前仍可能存在显式缺口。

point 用时间索引分别查找 `at` 前后最近候选，再选择时间差最小的一份。全局查询使用 `samples_time`，限定运行时使用 `samples_run_time`；后候选直接以 `max(cutoff,at)` 为唯一时间下界做索引定位，避免从保留窗口起点逐行过滤。默认允许误差为该运行实际采样间隔的两倍，返回实际采样时间和偏差。没有候选或超过容差时返回 `found=false`，不跨长缺口伪造快照，也不把不同指标分别取不同时间的值拼成一份快照。

原始区间查询示例：

```sql
SELECT run_id, seq, ts_ms, duration_ns, codec, payload
FROM samples
WHERE ts_ms >= ? AND ts_ms < ?
ORDER BY ts_ms, run_id, seq;
```

长范围查询必须使用聚合表；不能将 7 天原始快照全读出后才在 Go 中降采样。查询按索引边读边解码，不在内存中建立全量 7 天矩阵。由于每行保存整份快照，筛选少数指标仍需要解码候选行，不能宣称已经获得按指标列存的读取收益。

全局聚合查询已知只有一个候选运行时，直接按 `(run_id,step_ms,bucket_start_ms)` 主键范围读取，避免时间二级索引回表；多运行使用 `rollups_time`。候选运行按 raw、rollup 和 gap 的实际覆盖选择，配置起止墙钟不作为裁剪依据。

原始快照包含的自定义图表或热力图配置可能在重启后改变。响应按运行和配置版本分段；同版本可连续展示，版本改变时用对应配置绘制并断开，必要时让用户选择历史配置版本。

## 9. 实时与历史视图

前端状态分为“实时跟随”和“固定历史区间”，不再用一个 running 布尔值同时表示暂停和历史浏览。

- 保留 1m/5m/10m，增加 1h/6h/24h/7d 和自定义起止时间。
- 增加全局时间滑块、前后平移、图表横向缩放、起止时间输入和返回实时。
- 选中聚合桶展示摘要；点击具体时间或放大后查询真实单点。详情包含时间、单位、采样偏差及缺失状态。
- 历史画面不随实时消息移动；采集、落盘继续。暂停冻结当前窗口，仍允许用户拖动和查询其他历史区间。
- 所有图共享起止时间和选中时间游标，跨天坐标显示日期，详情显示完整时间与时区。
- GC 线始终表示采样时可见的最近一次 GC 时间，长窗口只保留桶内可见的最近事件；最多 120 条，不把它解释为全部 GC 次数或密度。
- 实时尾部缓存最近 15 分钟，另保留当前历史响应；实时缓存同时受 20000 样本和估算 16 MiB 上限约束，不按 7 天预分配数组。
- 交互请求做约 200ms 防抖，取消过时请求，使用请求代次防止旧结果覆盖新视窗。
- 视窗、滑块、预设、实时模式或配置改变时取消旧单点请求。手输绝对时间在所有运行中查找，点击具体配置图表才限定运行；默认容差由服务端按目标运行的采样间隔确定。

首次打开时先连接 WebSocket 并缓存尾部，再查询已提交历史。WebSocket 数据携带 run_id、seq 和 duration_ns，历史响应携带已提交水位，按样本身份去重并合并，不能只按时间戳去重。

新运行尚未出现在持久查询配置中时，实时尾部使用 WebSocket 配置中的聚合声明。累计直方图缺少前置样本或序号不连续时，不将跨缺口差值计为有效覆盖；保留逐单元覆盖和不完整标记，提示区间仅含已提交或有效部分。

重连后查询缺失序号覆盖的时间段，补齐数据库已保存的数据；仍未提交的尾部暂由实时缓存显示，并明确已落盘范围。新的 config 事件不应无条件清空当前固定历史视图或重复绑定导航事件。

## 10. 错误语义与运维状态

history/meta 至少包含：启用状态、最近成功提交时间、当前运行已提交序号、队列深度、丢样数量、最近存储错误、数据库/WAL 大小及实际可查询范围。

- 参数错误返回 400；请求超出保留窗口时返回被裁剪后的实际范围，完全无交集则返回空结果。
- 数据库暂不可读或查询超时返回明确失败，界面保留上一幅图并标记状态。
- WAL/数据库繁忙做有界重试；读请求有超时并响应客户端取消。
- 已知格式版本通过迁移升级，未知更高版本拒绝写入，不自动覆盖数据库。
- 一个数据库只供一个采集实例使用；连接级事务锁不能代替实例所有权约束。适配器打开数据库前获取跨平台进程文件锁 `<db>.lock`，关闭时释放；锁文件存在本身不代表仍被占用。

## 11. 实施顺序与验收

1. **采集与存储基础**：拆分不可变快照，增加运行和序号，完成 SQLite 迁移、原始写入、批处理及关闭刷新。旧实时行为保持可用。
2. **聚合与查询**：声明子序列语义，实现三个聚合层级、保留清理、点查询、区间查询、恢复与状态接口。
3. **前端历史能力**：增加范围、时间轴、固定历史状态、单点详情和实时尾部合并；补齐图表粒度与事件密度限制。
4. **集成和交付**：覆盖示例及自定义 handler 注册方式，更新 README，重建前端并重新生成 Go 实际嵌入的 `internal/static/dist.zip`。

必须验证：

- 用可控时钟验证恰好 7 天边界、批量过期与查询层立即过滤；不靠真实等待 7 天。
- 验证 250ms 和默认采样频率、重复时间戳、时间跳变、多个运行以及配置/桶边界变更。
- 用已知样本验证 gauge/rate 的时长权重、增量总和、直方图差分、峰值保留与首尾桶裁剪。
- 验证 point 返回同一实际快照、最近候选与容差，缺口处不插值、不跨运行求差。
- 验证事务失败回滚、幂等重试、强制退出后恢复、队列溢出、只读/磁盘写入失败以及 Close 刷新。
- 在带完整热力图的 7 天等量数据上验证索引计划、查询取消、清理与实时写入并发，以及内存、文件和 WAL 的变化。
- 验证历史与实时衔接、反复重连、快速拖动以及历史画面冻结时仍可操作。
- 用 CGO_ENABLED=0 验证目标平台构建；SQLite 驱动的编译体积和常驻内存计入监控开销。

性能目标需要在目标设备上确认：本地单点查询 p95 低于 100ms、7 天概览 p95 低于 500ms；采集线程不执行磁盘 I/O。记录引入前后的 CPU、内存、分配量及写入延迟，再确定缓存、压缩与查询预算默认值。这些是目标设备上的性能目标；当前交付验证不等于七天完整生产负载的容量或 p95 承诺。
